Regional Sales SQL
SELECT substr(created_at, 1, 10) AS order_day,
       COUNT(*) AS orders, SUM(amount_cents) AS revenue_cents
FROM orders
WHERE region = ? AND status = 'paid' AND created_at >= ?
GROUP BY substr(created_at, 1, 10)
ORDER BY order_day
Open Queue SQL
SELECT id, created_at, customer_id, amount_cents
FROM orders
WHERE status = 'open' AND created_at >= ?
ORDER BY created_at, id

04 / storage and maintenance

The faster reads require additional work on insertion.

The partial suite replaces the full queue index with an index containing open orders only (15,881 of 200,000 rows). It uses 7.85 MiB less than the covering suite while retaining the customer and regional covering indexes.

Insert timings measure 200 inserts inside an existing transaction, followed by rollback outside the timer. They isolate statement and index-maintenance work. They exclude commit/fsync, concurrency and durable transaction throughput.

05 / equivalent page results

A known cursor avoids skipping preceding rows.

SELECT id, created_at, amount_cents
FROM orders
ORDER BY id
LIMIT 50 OFFSET 180000;
SELECT id, created_at, amount_cents
FROM orders
WHERE id > :previous_id
ORDER BY id
LIMIT 50;

At offset 180,000, the measured medians are 1.594 ms for offset and 0.103 ms for keyset. The cursor is supplied before timing, as in sequential navigation. This does not provide arbitrary page-number access at keyset cost. The tests also cover deleted IDs and near-end pages.

06 / reproduction and limits

Inspect the inputs. Re-run the measurements.

Experiment controls

  • Seed 81427; one row per fictional order; timestamps have intentional ties.
  • Each suite starts from an identical database copy.
  • ANALYZE before measurement; automatic indexes disabled.
  • 3 warmups and 31 measured reads per query/configuration.
  • 32 MiB SQLite page cache; uncontrolled OS page cache.
  • Exact ordered result comparison before accepting timings.

Limits

One process, one local run and fixed query parameters. Configuration order is seeded, not counterbalanced. The workload is synthetic and does not model skew, concurrent writes, network latency or a production service.
